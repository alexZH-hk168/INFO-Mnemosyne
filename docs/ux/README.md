# UX 规格（写给开发 Agent）

这里的 UX 和 README 里给人看的介绍不同：它是开发时的施工图。**每个窗口、模块、弹窗、弹层和按钮各有一份 Markdown**，写清它从哪个上级进来、带进来什么数据，点了以后去哪个下级、调用哪个接口、改哪个前端状态。Agent 写某个组件之前必须先读对应规格。

## 命名

沿用 `界面级数-上一级进来的交互入口名称-概述`：

- **级数**：中间区的主页、对话栏、左侧两栏、右栏算 1 级；从 1 级点开的弹窗、弹层、面板、二级页面算 2 级，依此类推。按钮的级数等于它所在界面的级数。
- **入口名称**：在上一级上点的那个东西的名字，按界面文字写，如“开分支追问”“插件与 Skill”。
- **概述**：几个字说明它是什么。
- 例：`2-开分支追问-分支面板`＝从 1 级对话栏的“开分支追问”进入的 2 级分支面板。

同一个名字贯穿规格文件、组件注释、提交说明、截图文件名和进度日志。每份规格还有一个英文 ID（如 `chat.evidence-chip`），它同时是代码里的 `data-testid`。

## 每份规格的结构

1. **头部表**：ID、类型、级数、上级规格、概念图、建议组件路径、里程碑、规格状态。
2. **上一级：从哪里进来**：入口、触发条件、传进来的 props / 路由参数 / store 字段。另列“其他指向本规格的规格”（由生成器自动反查）。
3. **下一级：去哪里**：每个操作的结果、目标规格（链接）、调用的接口或 store action。
4. **接口**：REST、SSE 事件、query key，以及成功后要失效的 key。
5. **读写的前端状态**。
6. **状态**：空态、加载、出错、禁用等各长什么样。
7. **交互细则**、**验收**（逐条勾选）、**待确认 / 缺口**。

## 怎么改规格

规格由 [`tools/uxgen/`](../../tools/uxgen/) 从 Python 数据生成（`specs_a.py`～`specs_d.py`），生成器会检查上级与目标规格是否存在、名称是否重复。

```bash
python3 tools/uxgen/render.py      # 重新生成 docs/ux/specs/ 与 页面地图.md
```

- 改规格只改 `tools/uxgen/specs_*.py`，不手改生成的 Markdown。
- 规格与概念图冲突：画面以图为准，交互和接口以规格为准。
- 写代码时发现规格定不下来或和契约对不上：停下，在 [PROGRESS.md](../PROGRESS.md) 的“未决”里加一条并问用户，不在代码里自己拍板。
- 用户确认某份规格后，把对应条目的规格状态改为“已确认 · 日期”。
